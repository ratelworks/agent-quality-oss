# 자매 저장소(agent-safety-oss)와 같은 완성도로 올리기

기준은 자매 저장소 `agent-safety-oss` 2.4.0(2026-11-13)이다. 이 저장소는 0.4.3 이다.
이 명세의 모든 단위를 끝낸 뒤 한 버전으로 묶어 릴리스한다. 단위마다 버전을 올리지 않는다.

## 격차 (2026-11-16 실측)

| 항목 | 자매 저장소 2.4.0 | 이 저장소 0.4.3 |
|---|---|---|
| MCP 규격 | 2026-07-28 과 이전 규격을 한 서버가 함께 받음 | 이전 규격만. 등록된 입력 형식은 실행 때 검사되지 않음(52개 도구 모두 숫자 입력도 통과) |

## 결정

1. **문서 본문 생성을 추가한다.** 지금까지는 "문서를 직접 생성하지 않는다"였다. 품질관리자가 결재에 올릴 파일을 받으려면 본문이 있어야 하므로, 입력값을 양식 구조대로 채워 넣는 결정론적 생성을 추가한다. 문장을 지어내지 않는다 — 입력하지 않은 칸은 비워 두고 무엇을 적어야 하는지 알린다. 판정 수치를 만들지 않는다는 원칙은 그대로다. AI 가 쓴 본문도 검토·내보내기 도구에 넣을 수 있다.
2. **HTTP 서버는 유지하되 접근 경계를 둔다.** 자매 저장소에는 없는 표면이다. 기본은 실행한 컴퓨터에서만 받고, 밖에서 받으려면 명시적으로 켠다.
3. **법령 원문은 전 조문을 수록한다.** 조문이 전부 있어야 "없는 조문"을 단정할 수 있다.
4. **도구 수를 늘리는 것이 목표가 아니다.** 새 도구는 문서 생성·검토·내보내기, 품질시험기준 조회에 한정한다.

### 2. 접근 경계 (브라우저 폼·HTTP 서버)

- 브라우저 폼은 `127.0.0.1` 에서만 받는다. 요청의 Host·Origin·교차 사이트 표시를 검사하고 본문은 1 MiB 까지만 받는다.
- HTTP 서버는 기본으로 `127.0.0.1` 에서만 받고 본문 상한을 둔다. 밖에서 받는 것(주소·허용 출처·접근 토큰)은 환경 변수로 명시했을 때만 켠다.
- 보안 안내문을 실제 보관 동작(초안 저장 위치)과 맞춘다.

### 7. 근거 검증 3분류

고친 뒤 확인
- 같은 질문을 최종 설치본에 다시 던졌다: 슬럼프 180 배합 200 mm → 합격(155~205), 압축강도 공시체 3개 → 도구가 1회 시험값 26.4 로 보고 평균 조건을 되물음, 부적합 보고서 → 한 번에 깨진 값 없는 파일 저장. Haiku 로도 같은 결과.
- 마지막 차례(커밋한 설치본, 4회): 설계기준강도라고 물으면 도구에도 설계기준강도로 전달돼 호칭강도를 되묻는다. 차량 3대의 슬럼프를 한 문장으로 넣으면 판정하지 않고, 하나씩 넣으면 160 합격·175 경계·190 불합격으로 답한다. 아침 품질 회의 자료에 검측에서 확인할 내용이 실린다.
- 회귀 시험 `npm run test:usage` 110건을 전체 시험에 넣었다(값을 여럿 적은 문장 23개는 판정하지 않고, 값은 하나인데 호차·기온·기준 번호·회차·기준 표현이 섞인 문장 20개는 그대로 판정하는지 본다). 결함을 일부러 넣어 실패하는 것을 확인했다(값 묶음 잇기를 끄면 23건, 후보 수 확인을 끄면 15건 실패).

확인하지 못한 것
- 한글 프로그램에서 직접 여는 확인. 한컴 미리보기 엔진은 응답이 없어 중단했고, 문서 판독·조판 도구로만 봤다.
- Codex CLI 연결(쿼터를 아끼느라 돌리지 않았다). 두 세대의 실제 MCP 접속은 시험(16건)이 확인한다.
- 실제 현장 사용자의 질문. 이번 질문은 모두 작업자가 썼다.
- 한 문장에 같은 단위의 서로 다른 항목을 적으면("다짐도 96%, 함수비 12%") 값이 여러 개라고 되묻는다. 어느 수가 판정할 항목인지 이름으로 가리지 않는다 — 하나만 읽어 판정하는 쪽보다 안전해서 이렇게 뒀다.
- AI 비서가 도구의 답에 없는 계산을 스스로 덧붙이는 것은 막지 못한다. 작은 모델이 도구가 판정하지 않은 조건을 "27 − 3 = 24" 로 적은 답이 한 번 있었다(도구가 준 기준은 호칭강도 − 3.5).

### 15. 개선 실측 (2026-11-16 추가 — 대표 지시 "실제로 어떤점이 개선되었는지 확인해봐")

판정 수정을 세 번 연달아 올리려 하자 대표가 push 승인 대신 위와 같이 답했다. 내가 쓴 문장으로 내가 채점하면 편향되므로, 코드를 보지 않은 작성자에게 판정 규칙만 주고 현장 문장과 정답을 쓰게 해 버전별로 채점했다.

방법
- 묶음 둘: 맞춰 본 묶음 70문장(고치는 동안 결과를 봄), 보지 않은 묶음 80문장(고친 뒤에 처음 돌림 — 이 문장에 맞춰 고치지 않음). 저장소 `evaluation/field-judgment`.
- 정답은 PASS·FAIL·ASK(판정하지 않고 되물어야 함). 모든 버전에 같은 시험 주소를 주고 판정 도구를 불렀다.
- 버전: npm 게시본 0.4.0 · 오늘 첫 push(00fb9b4) · 공개 main(5c5e467) · 로컬 커밋(b9b6ec7) · 이 절의 수정을 넣은 것.

|---|---|---|---|---|

알게 된 것
- 공개 main 은 맞춰 본 묶음에서 틀린 합격이 0 이었지만 보지 않은 묶음에서는 틀린 합격 5 · 틀린 불합격 3 이 나왔다. 한 묶음의 0 은 0 이 아니다.
- 세 번째 검토 지적("공기량 4.5%, 재시험 6.5" 를 4.5 만 읽어 합격)을 받아 단위 없는 수도 후보로 세자, 맞춰 본 묶음의 정답이 61 → 53 으로 떨어졌다(되묻기 8건 증가). 지적은 참이었지만 그 수정만으로는 손해였다. 재지 않았으면 그대로 올렸을 것이다.
- 원인은 수가 무엇의 값인지 가리지 못하는 데 있었다. 고친 것: 수 앞에 적힌 항목 이름으로 그 항목의 값인지 가림("공기량 3.3 슬럼프 185", "함수비 11.2%"), 날짜(11/12)·측점 번호·조사가 붙은 세는 말·"0.3 넘었으니" 같은 기준 표현을 걷어 냄, 조건 값(호칭강도·기온)을 값이 같은 수가 아니라 적힌 자리로 걷어 냄, "32도" 를 온도 단위로 읽음, 측정값 후보가 없을 때 다른 수를 대신 집어 판정하던 길을 없앰.
- AI 비서를 붙여 값 두 개짜리 질문 3개를 던졌을 때는 공개 main 과 로컬의 최종 답이 같았다. 비서가 값을 스스로 나눠 넣었기 때문이다. 도구가 값 하나만 읽어 합격을 돌려준 호출은 있었다("노상 다짐도 96% (A구간), 노상 다짐도 92% (B구간)" → 96 으로 합격).

남은 것 (보지 않은 묶음에서 되물은 16문장의 갈래 — 이 문장에 맞춰 고치지 않았다)
- 전화번호 끝자리·납품서 번호 같은 잡수가 섞인 문장
- 표처럼 칸을 나눠 여러 시험 값을 단위 없이 적은 문장
- 회별 공시체 3개를 여러 줄로 적은 압축강도 기록
